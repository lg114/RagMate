# Redis 缓存策略笔记

本文记录 RagMate 问答接口的 Redis 缓存策略，Redis 版本为 7，部署方式为
单机 + AOF 持久化，不涉及集群分片。

## Cache-Aside：应用层维护缓存

采用 Cache-Aside（旁路缓存）模式，缓存的读写都由应用代码显式维护：

读流程：

1. 先查 Redis，命中直接返回；
2. 未命中查 PostgreSQL；
3. 把结果写回 Redis，并设置过期时间；
4. 返回结果。

写流程：先更新数据库，再删除对应缓存 key，下一次读请求重新回源加载。
删除而非更新缓存，是为了避免并发写导致缓存里长期残留旧值。写流程不
保证强一致，短时间内的读请求可能读到旧缓存，业务上可接受。

商品详情类 key 的 TTL 设为 300 秒。TTL 太短则缓存命中率上不去，太长则
数据更新后长时间读到旧值，300 秒是当前业务在两者之间的折中。

## 缓存雪崩：大量 key 同时过期

缓存雪崩指大量 key 在同一时刻过期，请求同时打到数据库，数据库瞬间被
压垮。典型触发场景是上线时批量预热的 key 用了相同的 TTL。

缓解办法有两个：

1. **过期时间加随机抖动**：在基础 TTL 上加 0–60 秒的随机值，例如
   300 秒 TTL 实际为 300–360 秒，key 的过期时刻被打散，不再同时失效。
2. **多级缓存**：Redis 之上再加一层进程内本地缓存，Redis 层整体失效时
   本地缓存仍能挡住一部分读请求，为数据库争取恢复时间。

抖动范围不宜过大：0–60 秒的抖动对 300 秒 TTL 来说是两成以内的波动，
命中率影响有限；抖动拉到数分钟级别，等于变相缩短了有效 TTL。

## 缓存击穿：热点 key 过期

缓存击穿指某个热点 key 过期的一瞬间，大量并发请求同时发现缓存未命中，
一起回源查数据库，单点被打爆。与雪崩的区别是：雪崩是**大量** key 同时
过期，击穿是**单个热点** key 过期。

推荐做法是互斥锁（mutex）：只有一个请求能拿到锁去回源重建缓存，其余
请求等待锁释放后重新读缓存，或者直接返回旧值：

```python
# 伪代码：SET NX 加锁，锁 30 秒自动过期，防止持有锁的进程崩溃后死锁
locked = redis.set("lock:product:123", "1", nx=True, ex=30)
if locked:
    try:
        data = load_from_db(123)
        redis.set("product:123", data, ex=300)
    finally:
        redis.delete("lock:product:123")
else:
    time.sleep(0.05)
    return redis.get("product:123")
```

锁的过期时间 30 秒是上限保护：重建缓存通常在 1 秒内完成，30 秒只防
持有锁的进程崩溃后锁永不释放。锁的粒度按 key 分，热点 key 之间互不
影响。

## 缓存穿透：查询不存在的数据

缓存穿透指请求查询数据库里根本不存在的数据：缓存查不到、数据库也查
不到，每次请求都穿透缓存打到数据库，攻击者可以用随机 id 批量制造这类
请求。

缓解办法：

1. **布隆过滤器**：在缓存前挡一道，判断 key 一定不存在的请求直接返回，
   不查数据库。布隆过滤器可能误判存在，但不会漏判不存在，误判的请求
   走正常回源流程即可。
2. **空值缓存**：数据库查不到时，把空结果也写进缓存，TTL 设短一些，
   例如 60 秒，避免同一不存在的 key 反复穿透。

两种办法可以叠加：布隆过滤器挡住绝大多数，空值缓存兜住误判的部分。

## 分布式锁 Redlock：多数派原则

跨多个 Redis 节点加锁时用 Redlock 算法：客户端依次向 5 个独立节点
申请锁，锁的过期时间相同；拿到超过半数（即至少 3 个）节点的锁，才算
加锁成功；否则依次释放已拿到的锁并重试。

Redlock 的正确性依赖各节点时钟大致同步，时钟漂移过大时锁可能提前
过期。单机部署不需要 Redlock，一台 Redis 上的 `SET NX` 加锁已经够用，
本文的互斥锁示例就是单机做法。

## 持久化：RDB 与 AOF

Redis 单机部署用 AOF 持久化，每条写命令追加到 AOF 文件。`appendfsync`
策略选 `everysec`：每秒刷盘一次，崩溃时最多丢失 1 秒的写命令，是性能
与安全的折中。`always` 每条命令都刷盘，写延迟明显上升；`no` 完全交给
操作系统，崩溃时丢失的数据量不可控。

AOF 文件会随写命令增长，Redis 在后台满足条件时自动重写（
`auto-aof-rewrite-percentage 100` 且 `auto-aof-rewrite-min-size 64mb`）：
当前 AOF 体积比上次重写后翻倍、且超过 64MB 时触发重写，重写过程用
新文件替换旧文件，期间的写命令先记入重写缓冲区。

RDB 快照作为补充备份：每天凌晨用 `BGSAVE` 生成一次 RDB 文件，恢复时
先加载 RDB 再重放 RDB 之后产生的 AOF，恢复速度比纯 AOF 重放快。RDB
是某一时刻的快照，`BGSAVE` 期间的新写入不会进入该快照，恢复点最多
落后到上一次快照时刻。

## 过期删除：惰性删除 + 定期采样

key 过期后不会立刻从内存消失，Redis 用两种机制清理：

1. **惰性删除**：访问某个 key 时先检查是否过期，过期则删除并视作
   不存在。冷 key 长期没人访问时一直占着内存，直到被定期采样扫到。
2. **定期采样**：每 100 毫秒左右从过期 key 集合里随机抽 20 个检查，
   过期比例超过 25% 时重复抽查，直到过期比例降下来或单次检查耗时
   触及 25 毫秒上限。

过期 key 堆积时内存占用虚高，`INFO stats` 里的 `expired_keys` 持续
增长而 `evicted_keys` 为 0，说明删除跟不上过期速度，先查采样是否被
慢查询挤占，再考虑缩短 TTL 或拆分 key 空间。

内存达到 `maxmemory` 上限时的淘汰策略由 `maxmemory-policy` 决定，缓存
场景常用 `allkeys-lru`：淘汰最近最少使用的 key。`noeviction` 策略下写
入新 key 直接报错，缓存场景不要用。

## Key 设计与大 key

key 用冒号分段命名，`业务:类型:标识` 三段式，例如 `product:detail:123`
表示商品业务的详情缓存。分段命名让 `SCAN` 按模式批量巡检成为可能，
也让不同业务的 key 不会互相撞名。

单个 key 的 value 不宜过大：一个 10MB 的哈希 key 上跑 `HGETALL`，会
一次性把 10MB 数据序列化返回，期间 Redis 单线程被占用，其他请求全部
排队等待。大 value 改拆分：哈希按字段拆成多个 key，或分页拉取（
`HSCAN` 游标遍历），单次操作的数据量控制在 KB 级别。

全量扫描禁止用 `KEYS *`：它会阻塞单线程直到扫完整个 key 空间，生产
环境 key 数量上万时一次 `KEYS *` 能让服务停顿数秒。改用 `SCAN` 游标
分批返回，每次返回一小批 key 与下一个游标，游标回到 0 表示扫完一轮。
`SCAN` 不保证同一轮内不重不漏，业务代码按“可能重复”处理结果集，
用集合去重后再使用。

key 的过期时间要和业务语义对齐：会话类 key 随用户登出主动删除，
不要只靠 TTL；配置类 key 几乎不变，TTL 设长（例如 1 小时）并配合
配置变更时主动删除。
